# `@clave/mobile-native`: what the two native phones share

Clave on the phone is two native apps, a SwiftUI app under `apps/mobile-ios` and a
Kotlin and Jetpack Compose app under `apps/mobile-android`, built on the same server
contract. This package holds what both read and neither owns, and no phone code:

| Folder                       | What it is                                                                                                                                                                                                                                   | Generated by                                            | Held in step by                                                                                                                |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `fixtures/`                  | the fixture vectors: the wire shapes and commands of the routes the prototype called (19 of the 27 a device session may call; `routes.json` lists all 27), as JSON samples exported from the real contract, and every shape as a JSON Schema | `scripts/export-vectors.ts`, under the repository's Bun | `vectors.test.ts`                                                                                                              |
| `assets/`                    | the desktop's design tokens, icons and fonts, generated for Swift and Kotlin                                                                                                                                                                 | `scripts/generate-assets.mjs`, under Node               | `assets.test.mjs`                                                                                                              |
| `scripts/fixture-server.mjs` | the fixture server both apps are tested against: this checkout's own server as a daemon with the Echo adapter, a local relay and a local OpenID Connect provider                                                                             | one command, below                                      | `fixture-server.test.mjs` (no daemon, relay or provider), `fixture-server.boot.test.mjs` (booted, with `CLAVE_FIXTURE_BOOT=1`) |

Everything under `fixtures/` and `assets/` is generated and committed. Never edit a
generated file: change the source (the contract, the stylesheet, the icon list), run
the generator, commit both. A generated file edited by hand fails its test, named.

```sh
npm run vectors --workspace @clave/mobile-native    # rewrites fixtures/ from the contract
npm run assets --workspace @clave/mobile-native     # rewrites assets/ from the desktop's sources
npm run vectors:check --workspace @clave/mobile-native   # exit 1 on drift, writes nothing
npm run assets:check --workspace @clave/mobile-native
npx vitest run packages/mobile-native               # the tests; the booted ones skip
CLAVE_FIXTURE_BOOT=1 npx vitest run packages/mobile-native/fixture-server.boot.test.mjs  # the fixture booted
```

## The fixture vectors

One file per contract family under `fixtures/`: `sessions.json`, `timeline.json`,
`requests.json`, `settings.json`, `files.json`, `push.json`, `events.json`,
`devices.json`, `relay.json`, `notify.json` and `routes.json`, plus `shapes.json`, every shape and command of those files as a JSON Schema (draft 7) made from the contract's own schema, and `index.json`, which names every file with its SHA-256 and size and the contract version they were exported from. A native test suite vendors the folder (or reads it from the checkout) and asserts its decoders and encoders against it. The samples say what the contract accepts today; `shapes.json` says what each shape is (the properties, which of them are required, the literals, the nested shapes under `$defs`), so a field the contract adds, drops or makes optional changes a committed file even when every sample still decodes. Its objects are left open (no `additionalProperties: false`): the contract accepts a payload holding a field it does not know and drops that field, so a phone's decoder accepts and ignores an unknown field too (on Android, `Json { ignoreUnknownKeys = true }`; Swift's `Codable` ignores one already). A rule with no JSON Schema form, such as the attachment path's NUL rule, is held by an invalid sample instead.

Every file carries:

- `family`, `contract` (the contract version), `notes` (what a reader of that family
  must know, in prose);
- `literals`: the members of the contract's literal types, read off the schemas
  (`AgentState`, `PairingRefusal`, `NotificationCategory`, the event tags), so an enum
  in Swift or Kotlin is checked against the list and not restated;
- `constants`: the paths, the close codes, the bounds and the timeouts, read off the
  modules (`PUSH_PATH`, `CLOSE_DEVICE_REVOKED`, `MAX_TRANSFER_BYTES`, `RELAY_*`);
- `shapes`: keyed by the contract's own exported schema names (`Session`, `SessionEvent`,
  `SessionStream`, `HistoryPage`, `SessionInfo`, `TimelinePage`, `SessionPosition`,
  `PendingRequest`, `RequestSnapshot`, `LaunchProfilePreferencesView`,
  `WorkspaceStateView`, `FileText`, `ClientFrame`, `ServerFrame`, `ServerEventEnvelope`,
  `DeviceDescription`, `DeviceView`, `DeviceSessionView`, `MachineList`,
  `NotificationPayload`, and the others of each family). Each has `valid` samples, which
  a phone's decoder must accept, and `invalid` samples, which it must refuse, each with a
  `name`, the `wire` JSON and, for an invalid one, `because`;
- `commands`: keyed by the contract's command and query names (`StartSession`,
  `WriteSession`, `GetSessionTimeline`, `ResolvePendingRequest`,
  `RequestDevicePairing`, …): `payload` samples the phone sends (valid), `invalidPayload`
  samples the server refuses, `success` samples it answers, and `failures`, the declared
  failures as a 422 body carries them (`{"_tag": "SessionWriteUnknown", …}`). A query is
  a GET with its payload as query strings, so its numbers are strings on the wire; a
  command is a POST with a JSON body.

`wire` is the JSON exactly as the contract's own schema encodes it: every valid sample was
decoded through the schema at export time and written back from the decoded value, every
invalid sample was proven refused, so a sample that contradicts the contract never lands
in a file. The decoded value differs from the wire in two places: terminal bytes are base64 on the
wire (`SessionStream` of kind `pty`) and bytes in memory, and a query's numbers are strings
on the wire (`NumberFromString`) and numbers in memory.

Two blocks are not the contract's and say so. `timeline.json` carries `ordering`: the
pages a phone must refuse by the ordering rule of `docs/mobile-timeline.md` (a page mixing
generations, reversed or repeated positions, a position above the cursor), which the
contract accepts; `routes.json` carries the server's device scope
(`packages/server/src/devices/scope.ts`): every route of the API with the method, the
path, the command behind it and whether a device session may call it, the allowlist as
`scope.GET` and `scope.POST` (`/files/*` for the prefix), the refusal sentence, and the
event tags a phone hears and does not hear.

The owner-only commands a phone never calls (approve, refuse, revoke, the relay address,
the notify routes) are under `owner` in `devices.json` and `notify.json`, so a client
knows what refuses it with `A phone may not do this.`

## The assets

- `assets/tokens.json`: the four themes (`dark`, `light`, `coffee`, `charcoal`) with
  their colour roles as lowercase hex or `rgba(r, g, b, a)`, the shared roles, and the
  control, frame, radius, control-height and sidebar specs resolved to pixel numbers,
  all read from `packages/ui/src/tokens.css`. The desktop's `--font-weight-medium` is
  400, and the one face is Geist (`typography.fontSans` is the desktop's CSS family,
  `Geist Sans`, an alias the font files do not carry: register and look the faces up by
  the names in `fonts/fonts.json`).
- `assets/icons.json`: the path data of the 36 Heroicons (24/outline, from the very
  `@heroicons/react` modules the renderer imports) and the 4 provider marks of the
  desktop's `cli-logos.tsx`, with one `assets/icons/svg/<name>.svg` and one Android
  vector drawable `assets/icons/android/ic_<name>.xml` (lowercase, underscores) per
  glyph, drawn white and tinted at render time the way the desktop paints
  `currentColor`. Adding an icon is one name in `ICONS` of `scripts/generate-assets.mjs`
  and a run.
- `assets/fonts/`: Geist at the three weights the desktop loads (`Geist-Regular.otf`,
  `Geist-Medium.otf`, `Geist-SemiBold.otf`), unwrapped from the `@fontsource/geist-sans`
  WOFF files into OTF by `scripts/woff-to-otf.mjs` (no Python, no dependency), with the
  licence `OFL.txt` beside them and `fonts.json` naming the package version, the Geist
  release (`geistRelease`), the upstream repository, the family the faces register under
  (`family`, `Geist`, read from each file's own name table, beside `cssFamily`, the
  desktop's alias), and each face's PostScript name (`Geist-Regular`, `Geist-Medium`,
  `Geist-SemiBold`, what `UIFont(name:)` and `Font.custom` take) and SHA-256. Geist is
  under the SIL Open Font License 1.1. **Never add the Sentient or Synonym files here**:
  their licence allows no redistribution through a repository (AGENTS.md, Type).

The generator removes any file under `assets/` it did not produce, so the folder is
always exactly its output.

## The fixture server

```sh
node packages/mobile-native/scripts/fixture-server.mjs \
  --server 47301 --relay 47302 --issuer 47303 --tmpdir /private/tmp/clave-native-c
```

One command starts three processes on the band of ports the caller names, with the real
sign-in and the real pairing and nothing bypassed, after checking that the daemon it starts
can reach no provider:

1. the local OpenID Connect provider of `tests/e2e/fixtures/oidc-provider.mjs` on the
   issuer port, its dynamic registration taking any redirect URI a client sends
   (`clave-ios://oauth/callback` and `clave-android://oauth/callback` both register), its
   authorization endpoint approving on sight, its tokens RS256-signed with a key it
   publishes;
2. the relay (`apps/relay/src/main.ts`) under the repository's Bun, with that issuer;
3. this checkout's server entry (`apps/server/src/main.ts`) as a daemon under Bun with
   `--dev-echo-adapter` (a deterministic chat that repeats what it is told and raises no
   request), `--push-fake` (the recording push transport), `--relay` naming the relay, a
   token file of the fixture's own, and the three flags below.

Then it signs the daemon in as the fixture owner (`fixture-owner`,
`owner@fixture.clave.test`) through the daemon's own `POST /accounts/antasphere/sign-in`,
the provider standing in for the browser; waits until the relay lists the machine
online; registers `<tmpdir>/scratch` as a workspace; starts an Echo chat on it and writes
one message carrying a nonce (`seeded-<nonce>`, client message id `m-fixture-<nonce>`),
waiting for the Echo's reply in the ordered timeline; and prints one line per value:

```
CLAVE_FIXTURE_SERVER_URL=http://127.0.0.1:47301
CLAVE_FIXTURE_TOKEN_FILE=/private/tmp/clave-native-c/server/daemon-token
CLAVE_FIXTURE_RELAY_URL=http://127.0.0.1:47302
CLAVE_FIXTURE_ISSUER_URL=http://127.0.0.1:47303
CLAVE_FIXTURE_MACHINE_ID=m_…
CLAVE_FIXTURE_WORKSPACE_ID=ws-…
CLAVE_FIXTURE_SESSION_ID=…
CLAVE_FIXTURE_NONCE=…
CLAVE_FIXTURE_RECORDER_LOG=/private/tmp/clave-native-c/stubs/recorder.log
CLAVE_FIXTURE_FILE=/private/tmp/clave-native-c/fixture.json
```

The token file is a path: the daemon's token is in it (mode 0600) and never on stdout.
A runner that must act as the owner (approve a pairing with `POST /devices/approve`,
revoke a phone, read `GET /devices`) reads it from there. `fixture.json` holds the same
values as JSON, with the owner's identity, the two redirect schemes, the daemon's flags
and announcements, the names of its environment variables (never their values) and the
checks. Ctrl-C stops the three processes. The data folder (`<tmpdir>/server`, with the
daemon's identity, its keychain file on macOS and its relay credential; `<tmpdir>/relay`;
`<tmpdir>/scratch`; `<tmpdir>/stubs`) is the fixture's state and survives a restart: the
token, the server id and the machine id stay the same, the daemon registers and signs in
anew (the provider's registrations live in its memory), the chat is seeded again. Remove
the folder to start over. Nothing the fixture cleans lies outside what it created: the three
owned folders and the recorder log under `<tmpdir>/stubs` (and `<tmpdir>/stubs/elsewhere-home`
under the `divergent-home` mutation), the daemon's stored registration and session under
`<tmpdir>/server`, and in its tmux folder only what the paragraph below names.

**No real agent, no real login, and the proof of it.** The daemon names every fresh chat by
its first message with a `claude -p` one-shot (`packages/host/src/title-generator.ts`), the
Echo chat included, under the login shell's PATH and the machine's own login; it polls Claude
and Codex usage on a clock from five seconds after its start; and an explicit usage read goes
through the machine login's keychain item. The fixture keeps all three off:

- it starts the daemon with `--no-titles` (the daemon's explicit title opt-out, checked at
  the title generator's every entry), `--test-no-activate` (no usage clock, the test fixture
  route on) and `--test-no-machine-usage` (an explicit Claude usage read never reads the
  machine login); the daemon announces the three in its discovery file as `titles: "off"`,
  `testMode: true`, `machineUsage: false`;
- the daemon's environment is built from an allowlist and nothing of the calling shell's
  beyond it: `USER`, `LOGNAME`, `TMPDIR`, `LANG`, `LC_ALL`, `LC_CTYPE`, `TERM` and `TZ` as
  they are; `HOME`, `<tmpdir>/stubs/home`, a folder of the fixture's own recreated empty at
  every boot, so the daemon's readers that find the home through `os.homedir()` or `HOME`
  (`~/.claude/projects`, `~/.claude.json`, `~/.codex/auth.json`, the analytics plugin it
  forks with that `HOME`) find the fixture's folder and never the person's; `SHELL`, a
  script named `zsh` under `<tmpdir>/stubs` (the daemon reads its login environment through
  `$SHELL -lic 'env -0'`, and only a POSIX shell's name is kept) that answers the login
  environment written into it at the install, under `env -i`, whatever environment it is
  run with, and runs a `-c` command on that same environment; `PATH`, the stubs folder then
  the system directories, so the **recorders** `claude` and `codex` are the only ones the
  daemon can find (every invocation appends one line, time, command, first two arguments,
  never the stdin, to `<tmpdir>/stubs/recorder.log`); `CLAUDE_CONFIG_DIR` and `CODEX_HOME`,
  two more folders of the fixture's own recreated empty at every boot; `TMUX_TMPDIR`, the
  fixture's tmux folder (below); the issuer; the keychain file on macOS. The login
  environment the stand-in answers is all of it less the last two, the daemon's own
  settings, which it reads from its process environment and no child of it needs. Both Bun children start with `--no-env-file`, so no `.env` of the
  working directory reaches them past the allowlist. The plugin runners the daemon forks
  inherit the flag: Bun 1.4.1's `fork` hands its runtime flags on (probed on a Mac: a `.env`
  planted in the child's folder was read without the flag and not with it). Nothing here
  claims it for any other descendant.

**tmux's sockets are the fixture's.** At its start, and whenever it lists the sessions it
could adopt, the daemon asks a tmux it finds for the sessions of its `clave` socket
(`packages/host/src/sessions/adapters/pty-backend.ts`, `liveTmuxSessions`), and the person's
own Clave keeps its sessions on a socket of that name. tmux 3.5a builds the socket's path as
`<TMUX_TMPDIR>/tmux-<uid>/<name>` from the first of `$TMUX_TMPDIR` and `/tmp` that resolves
(`tmux.h`, `TMUX_SOCK`; `tmux.c`, `expand_paths` and `make_label`): a value unset, empty or
naming nothing is dropped and `/tmp` is used, the person's own sockets, and a symlink is
followed wherever it points. So the daemon and the login environment of its stand-in shell
both carry `TMUX_TMPDIR`, the fixture's **tmux folder**: `/tmp/clave-fixture-tmux-<12 hex of
the stubs folder's real path>` under the real `/tmp` (`/private/tmp` on macOS), outside the
run folder so every socket's name fits a socket address (104 bytes on macOS, 108 on Linux)
whatever the run folder's length. A missing one is made with mode 700 and a marker,
`.clave-native-fixture-tmux`, naming its stubs folder. One already there is taken only when it
is this user's plain folder, mode 700, carrying exactly that marker, its lease (`.lease`, the
pid of the fixture holding it) held by no live process, no socket anywhere in it and nothing
the fixture never makes; then only what a past run left is removed, the lease and the empty
folders a tmux client and the decoy leave, one at a time and never recursively. Anything else
is refused, exit code 2, before a byte is written. A boot holds the lease from its install to
its stop and gives it back on every way out; a dry run takes none. The folder stays with its
run folder: remove both to start over. What rests on tmux's source and what was seen apart:
the fallback to `/tmp` and the socket's path are read from tmux 3.5a's source, never seen by
asking a socket; the fixture asks no tmux anything and starts none. On this Mac the stand-in's
PATH reaches no tmux (Homebrew's is in `/opt/homebrew/bin`), so a fresh run folder's daemon
finds none, while a reused data folder may keep the path a past daemon found
(`<tmpdir>/server/tmux-path.json`): either way the socket's folder is the fixture's.

It checks in two stages, prints every check as `check ok` or `check FAIL`, and **refuses to
go on unless all pass** (exit code 2). Before any process starts (`preflight`): (1) the argv
the daemon will get carries the three flags; (2) both the environment the daemon will get
and the login environment its shell answers, read the way the daemon reads it, name the
fixture's home as `HOME`, resolve `claude` and `codex` to the recorders and carry exactly the
fixture's tmux folder as `TMUX_TMPDIR`, a folder that exists by its own real path, this user's
with mode 700, other than `/tmp` itself, holding only its marker and its lease, with room for
the `clave` and `default` sockets' names. After the daemon
announced itself and before any chat (`bootChecks`): (3) the discovery file says titles off;
(4) it says the test mode on and the machine usage off, and the daemon answers
`POST /e2e/evaluate`; (5) asked of the daemon itself through its test
hooks, the title one-shot's own resolver (the daemon's cached login environment, the one-shot's locate) names the recorder `claude`, the cached login PATH names the recorder `codex`, the daemon's own `PATH` starts with the recorders' folder, and the daemon's `SHELL` is the fixture's `zsh` under a name the daemon runs a command through (the host's `POSIX_SHELLS`: any other name would send the Codex read to the real `/bin/zsh`); (6) asked of the daemon itself, the keys of its environment are the allowlist's and the fixture's own and nothing else (names compared, never values); (7) asked of the daemon itself, `os.homedir()` and `HOME` both resolve to the fixture's home and `TMUX_TMPDIR` is exactly the fixture's tmux folder, still its own real path (compared inside the daemon, which answers yes or no and never a path); the folder holds no socket, and the check says whether a tmux client of the daemon made its `tmux-<uid>` folder there, which tmux does in the folder it chose. `--preflight` runs the first two alone on the folder's stubs and exits, starting no daemon, relay or provider (the stand-in shell runs, as the daemon would run it): the way for a lane to show its worktree's stance before its first boot. A folder the fixture may write and clean is one it created, or one it marked: a regular file `.clave-native-fixture` at its root holding exactly the fixture's stamp (read with `lstat`, so a symlink is refused); a folder holding anything else and no marker, or a marker naming another owner, is refused with exit code 2 before a byte is written, and a dry run on a folder it reuses rewrites nothing while the install there is complete (the shell, the two recorders, the recorder log and the home); an incomplete one is installed again, its recorder log and owned folders emptied.

**While it runs, the recorder guards every mode.** The first line a recorder writes, in the plain run or under `--approve`, is printed and the fixture stops the three processes and exits 3; a read of the log that fails (the file gone or unreadable) stops them the same way, a failure and never "no calls" (the log exists, empty, from the install on). The enforcement is continuous, never a dry run.

`--check` seeds the chat, waits past the clock's first tick and asserts: zero recorder
lines, no `session.title_changed` for the chat on the push channel, the two owned credential
folders still empty and the fixture's home without `.claude`, `.claude.json` or `.codex`, no
usage event on the push channel; then an explicit Claude usage read answers
an error without the machine login and adds no `claude` line to the recorder (a line from
before the read, a title one-shot under a mutation, is the first row's), and an explicit Codex
usage read reaches the codex recorder (exactly one line) and answers an error. Each row says
what it rests on: `argv`, `announced` (a flag the daemon states, derived from the code), `observed` (what the fixture saw of the daemon's own environment or resolver), `recorder`, `wire` or `owned-folders`; no row rests on a provider's answer, none being expected, and the person's own folders (`~/.claude`, their Codex home) are never read. The recorder log is the evidence that no CLI ran; the owned folders staying empty is a supporting observation beside it, never a zero-call guarantee of its own.

`--mutate <name>` is the verifier's knob, never a configuration, and no mutation boots the
daemon with the usage flags dropped against this Mac's login: `drop-title-opt-out` boots
without `--no-titles` (the recorders in place, both usage flags kept), fails the first and
third checks, and is refused before any chat, nothing reaching the recorder: the one-shot
itself is `bypass-title-guard`'s to show; `bypass-title-guard` keeps every
flag and re-opens the titles through the daemon's test-mode hook, so the daemon still
announces titles off while the one-shot really runs and the recorder alone catches it;
`start-usage-clock` starts the clock through the test hook with every flag kept and shows
the codex recorder and the usage events (the flags are kept because the machine login's
keychain item is read by username through `/usr/bin/security`, which no environment
variable redirects: a clock run without them would read the person's own login);
`divergent-daemon-env` passes the preflight on the recorders' environment and starts the
daemon on the calling shell's PATH instead, so the fifth check fails and nothing is seeded;
`divergent-home` passes the preflight on the fixture's home and starts the daemon with
another empty folder of the fixture's own as `HOME` (`<tmpdir>/stubs/elsewhere-home`, never
the person's home), so the seventh check fails and nothing is seeded;
`divergent-tmux-tmpdir` passes the preflight on the fixture's tmux folder and starts the
daemon with a decoy as `TMUX_TMPDIR`, a folder of the fixture's own inside the tmux folder,
made with mode 700 before the daemon starts and held to the same conditions tmux puts on a
folder, so no socket can fall back to `/tmp`: the seventh check fails and nothing is seeded;
`drop-recorders` starts no daemon, relay or provider: the second check aborts first; nor does
`drop-tmux-tmpdir`, which takes `TMUX_TMPDIR` out of the daemon's environment: the second
check aborts first. No mutation starts a daemon without `TMUX_TMPDIR`. The test runs the
eight, and the running-mode guard once.

Options: `--approve` approves every pending pairing as it appears (off by default; the token file is the way otherwise); `--check`; `--preflight`; `--json`, one JSON object instead of the lines, the checks included; `--timeout <ms>`, how long each process may take to announce itself (90 s by default). Exit codes: 2 a refused boot or a refused run folder, 3 the recorder caught an attempt while running or its log could not be read, 1 a failed proof or an error. A port of 0 takes a free one; without `--tmpdir` a fresh folder under the system
temporary directory. On the Mac, the iOS simulator reaches `127.0.0.1` directly; the Android
emulator needs `adb -s <serial> reverse tcp:<port> tcp:<port>` for the three ports: the
provider listens on `127.0.0.1` and names `http://127.0.0.1:<issuer port>` as its issuer, so
reached through `10.0.2.2` its discovery document names another origin and a strict issuer
check refuses it. A result on the Echo fixture proves the protocol, never a real provider
or a physical phone.

The secrets of the daemon never reach the login keychain: on macOS they go to a keychain
file under the data folder (created by the fixture with `security create-keychain`), on
Linux to the daemon's encrypted files. The provider is never the production hub.

## The CI entry of a native app

`.github/workflows/mobile.yml` builds and tests each native app through one executable
file at the root of its folder, owned by the app: `apps/mobile-ios/ci.sh` and
`apps/mobile-android/ci.sh`. The contract:

- the workflow runs `bash apps/mobile-<platform>/ci.sh` from the repository root;
- the iOS job runs on `macos-26` with `DEVELOPER_DIR=/Applications/Xcode_26.0.1.app/Contents/Developer`
  (Xcode 26.0.1, build 17A400, Swift 6.2) exported; the Android job runs on
  `ubuntu-latest` with Temurin JDK 21 (`JAVA_HOME` set by `actions/setup-java`), Gradle's
  cache (`gradle/actions/setup-gradle`), the runner's `ANDROID_HOME`, and `sdkmanager` on
  the `PATH`, so the script installs the platform and build tools it pins into it (the
  versions are the app's, in its own `ci.sh`);
- the script builds the app and runs its tests, prints its counts, and its exit code is
  the verdict; the results it leaves under `build/` are kept as artifacts for seven days;
- a folder without `ci.sh` makes its job skipped, with a notice on the checks page, so the
  workflow landed before the apps did and a green app check always means the app's own
  entry ran; once a folder holds files, `npm run check:structure` requires the entry as a
  regular file and refuses a `package.json` anywhere inside a native app (build output left
  out).

The Linux job runs this package's tests, the booted fixture with `CLAVE_FIXTURE_BOOT=1`
(set on the step; a CI step without it fails one case rather than skip the boots), the
vectors and assets checks, the
structure guard, the package's lint and the node typecheck.
