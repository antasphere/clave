# ADR 0003: the server apart from the client

Status: accepted, 2026-10-02 (wave 1 of the split: the shell boots `@clave/server` in-process or attaches to one running on its own, and the suite drives both); amended the same day from lane A's gate (runtime-agnostic server layers, the push channel on the server's own port); amended 2026-10-06 by wave 2's lane A (the sessions on the server, the framework at 0.3.0, the attached endpoint published: the section "Wave 2: the sessions on the server" below) and by its lane D (the settings served: the section "Wave 2: the settings on the server" below); amended 2026-10-08 by wave 3's lane B (the terminal process beside the standalone server: the section "Wave 3: the terminal process" below); amended 2026-10-08 by wave 3's lane A (the workspace files served: the section "Wave 3: the workspace files on the server" below); amended 2026-10-10 by wave 4's lane B (every server-event listener joins the server whenever the window opened: the section "Wave 4: a window hears the server whenever it opens" below); amended 2026-10-10 by wave 4's lane A (the stop, the quit and the end-to-end run bounded: the section "Wave 4: a quit and an end-to-end check that cannot stall" below)

## Context

Clave is one Electron program. Measured on `dev` at fb8abba: a main process of about 44k lines in which 71 modules import `electron`; a flat preload of 291 methods over 235 IPC channels, called from 489 sites in 108 renderer files, with no client wrapper; the sidebar truth (groups, tabs, layout) in each window's renderer store, so the MCP server answers 20 of its tools by asking a renderer; about 25 JSON files under the user-data directory, each written by its own manager; secrets through Electron's `safeStorage`. The sessions module (`src/main/sessions/`) is the one seam already shaped like a wire contract. The end-to-end harness proves the app by reaching inside that one process (`app.evaluate` on `ipcMain` and `BrowserWindow`), so any change of transport breaks every spec.

Valentin, 2 October 2026: "Right now clave is running as a single program, everything in an electron app. I want to be able to split server from the client. You shall use @structure-ai framework for event messaging."

`@structure-ai` 0.2.1 (Ligerian-labs/structure) is Effect 3.22 and Effect Schema. Its event messaging is domain events on aggregates, an event store with projections, a transactional outbox and an idempotent inbox, schema-typed command and query buses. Two measured facts shape the split: the framework pushes nothing to a client (no WebSocket, no SSE; `http.serve` takes raw mounts but exposes no upgrade hook), and node-pty, from the app's own `node_modules`, loads under Bun 1.3.14 and never emits a byte, while under Node it works.

The full record, with the nine decisions and the measurements behind them, is the spec `knowledge/specs/2026-10-02-server-client-split.md` on `clave-os`.

## Decision

The server is a package on the framework, and the split is a strangler: the server first runs in-process inside Electron main behind the bus, then as its own process. Every lane merges into `dev` and the app works at every merge. There is no `[major]` release marker until the out-of-process server ships to users; the framework is pinned at 0.2.1.

### What is event-sourced, and what is not

Workspaces, groups, tabs, session records, accounts, launch profiles and preferences are aggregates with projections; the sidebar is a read model. PTY bytes, provider frames, usage reads and git status are ephemeral streams, never in the event store. The event store is in memory in wave 1.

### Runtime and the push channel

The server's layers are runtime-agnostic and the listener comes from an adapter: Node when the server runs inside the app, Bun when it runs alone. The PTYs stay with a Node process until a Bun-native PTY is proven. The push channel is one WebSocket upgrade on the server's own HTTP port, owned by Clave, carrying server-to-client events and session bytes with reconnection and per-session subscriptions. A second WebSocket handler on that port corrupts frames, so nothing in the shell and nothing in the harness listens on or upgrades that port.

### Topology and secrets

A local daemon on the loopback with a bearer token, the MCP server's shape, spawned and attached by the app. Reachability from another machine is designed for and not built. Secrets at rest go through a secret port with two adapters: `safeStorage` while the server runs in-process, the macOS Keychain through the `security` CLI for the standalone server. The new contract is Effect Schema; zod stays where the renderer still reads it and retires lane by lane.

### What stays Electron's

Windows (`window-registry.ts`, `window-routing.ts`, `window-state.ts`), the app menu, the auto-updater, view guests, the preview protocol, dialogs, clipboard, notifications, the haptic and mission-control helpers, and the plugin host in these two waves. The renderer keeps `window.electronAPI` for those.

### How the shell gets its server

`src/main/server-boot.ts`, called once at `app.whenReady`:

- **In-process**, the default and what the shipped app does: the shell calls `startClaveServer` (`src/main/server/clave-server.ts`, lane A's), which starts `@clave/server` on Node's own listener over the session manager, publishes the address to the windows, and gives the boot the url, the token and `stopClaveServer`.
- **Attached**, under `CLAVE_SERVER_URL` with `CLAVE_SERVER_TOKEN`: the shell uses a server somebody else started and starts none of its own. It registers on it and the harness proves the boot, but it publishes no address to the windows in this wave: a standalone server has no sessions until the sessions move to the server (wave 2), and a window routed to it would list none and lose its chat view. The windows stay on IPC; publishing to them in attached mode is wave 2's, with the sessions lane.

Either way the shell then registers itself with the server (`POST /clients`, as `shell`, named `clave-shell <version>`, with its pid) and writes `clave-server.json` in the user-data directory (the url, the token, the mode, `ok`, the client id; mode 0600, write-then-rename, after `mcp-server.json`). On quit it waits for a boot still in flight, deregisters, and, when the server is its own, stops it.

The token belongs to what is meant to call the server: the shell, the client, the harness. It lives in that file and in the shell's handle, and the renderer's client gets it from main over IPC alone, on the channel the contract names (`server:endpoint`, answered with `{ url, token }` or null while there is no server). The two variables an attach is asked with are read once at boot and taken out of the main process's environment there, before anything spawns. An export into that environment would reach every helper main spawns off `process.env` (git, `gh`, the Codex app-server, the plugin runner) and none of the sessions, which get their environment from the login shell read once at boot and from tmux's own `update-environment` list; neither is wanted.

### How the window reaches the server

The preload runs with Node available (`sandbox: false`), and its routed calls leave through Node, not through the page: the request client goes out through `@effect/platform-node`'s HTTP client (`createApiClient` takes the layer; a browser page keeps `fetch`), the push socket through `ws`. Nothing of the window's origin travels, so the packaged `file://` page sends no `Origin`, meets no Content Security Policy and no preflight, and `src/renderer/index.html` keeps `default-src 'self'` with no `connect-src`. The round-2 verifier watched the alternative fail: the moment the shell published its server, the page's own fetch was refused by its CSP and, behind it, the server's preflight refused the page's opaque `null` origin, and the chat view never mounted.

The server's cross-origin rules stay for browser pages (the dev renderer on `http://localhost:5173`, a browser client later), with one rule added: a preflight is decided before the token check, whatever the origin. A loopback page gets its answer with the headers it asked for; any other `Origin` on an OPTIONS, the opaque `null` of a sandboxed frame or a page from another site, is answered 403 with no CORS header and never reaches the token check; an OPTIONS with no `Origin` is not a preflight and meets the token check like any request. No `null` origin is ever accepted: a sandboxed page from another site on this machine must not reach the server, which is what lane A's round 3 closed. The push handshake takes loopback pages and clients with no Origin only: since the packaged window's socket leaves through Node, a `file://` Origin is refused too, so an HTML file opened locally in a browser cannot hold pre-hello sockets on the port. A session or an agent that must reach the server is handed the address deliberately, when the sessions move to the server (wave 2), and the server spec pins the claim: a terminal the app spawns sees neither variable.

An attach that fails (nothing answers the url, or the token is refused) is never papered over by starting the in-process server instead. The app runs without a server, the failure is in the log, in the discovery file as `ok: false` with the url that was asked for, and on screen as a notification outside test mode. In this wave nothing the window shows comes from the server, so the app stays usable; once the domains move, a server that cannot be reached is a boot failure.

### What the shell expects of the server

The shape lane A's contract carries (`packages/contract/src/clients.ts` and `api.ts`: the clients group beside the framework's health group), as the server answers it in both shapes:

| Call                                   | Answer                                       | Token  |
| -------------------------------------- | -------------------------------------------- | ------ |
| `GET /health/live`                     | 200 `{ status: "live" }`                     | none   |
| `GET /health/ready`                    | 200 `{ ready, checks }`                      | none   |
| `POST /clients` `{ kind, name, pid? }` | 201 `{ id, kind, name, pid?, registeredAt }` | bearer |
| `GET /clients`                         | 200 an array of those, oldest first          | bearer |
| `POST /clients/unregister` `{ id }`    | 204, or `ClientNotFound`                     | bearer |

`kind` is one of `shell`, `browser`, `agent`, `other`; the Electron shell registers as `shell`, named `clave-shell <version>`, with its pid. Bound to 127.0.0.1. A wrong or missing token is a 401, compared in constant time. The push channel is a WebSocket upgrade at `/push` on that same listener, lane A's; the shell and the harness never upgrade it.

### The server as its own process

`scripts/server-process.mjs` is the one place that names the command, for the dev script and the harness alike. The process binds the loopback, writes `clave-server.json` into its `--data-dir`, and prints one JSON line `{"url","token"}` on stdout once it listens; whoever started it hands the pair to the app. The command runs `src/main/server-entry.ts` under Bun, which runs the TypeScript as it is: `@clave/server`, the same package the app runs in-process, over an empty session source, because until the sessions move to the server (wave 2) a standalone server has none to answer for; a client sees the same API, the same token check and the same push channel either way. `npm run dev:attached` starts the server and `electron-vite dev` attached to it and stops both together; `npm run dev:server` starts the server alone and prints the two variables for a dev app started by hand. The server's dev data lives under `~/.clave/server-dev`.

### The harness

`tests/e2e/harness.mjs` runs the suite two ways, and the way is `CLAVE_E2E_SERVER`: `in-process` (the default) or `attached`, where `launchApp` starts one server per spec on its own data directory and port before the app and stops it with `app.close()`. A spec that must prove one path whatever the suite runs passes `server: 'attached'`, `'in-process'` or `{ url, token }`. In in-process mode a stray `CLAVE_SERVER_URL` in the caller's shell is dropped, so the app never attaches by accident. `serverEndpoint(dir)` reads the discovery file; `serverClient(url, token)` is the server's HTTP API, and it is how a spec asserts on the server, never a hook inside main. `run.mjs` names the mode on both ends of its output. `listeningPorts(pid)` asks the OS what the main process serves, which is how a fallback on another port would show. `tests/e2e/server-boot.spec.mjs` proves four things, in-process and attached: the app is on its server and a spawned terminal sees no token; an attached app registers and deregisters; a dead url leaves the app on the MCP port only; a quit during a slow registration leaves no ghost client. Its header says which mutation turns which line; the round-1 verifier proved six of eight and the two it did not are now pinned (the ports, the crash rule below).

`run.mjs` reads `tests/e2e/known-failures.json`, the named failures of `dev` itself: `specs` lists the checks that fail on every machine we measured, by spec and check name, printed `KNOWN` and counted apart; `unstable` lists the specs that crash before finishing or fail differently from one run or machine to the next, printed `UNSTABLE`, counted apart, and explicitly not a gate until fixed. A `<spec> ran to completion` check can never be listed as known: it is the runner's own, raised when a spec throws, and listing it would absorb every crash of that spec with exit 0. A listed check that passes, or an unstable spec that passes in full, is reported at the end so the file shrinks. Measured on 2 October 2026 on `dev` at fb8abba: 25 failing checks on a laptop, 28 on `macos-latest`, 15 in common; 10 checks in 7 specs are known, 11 specs are unstable. The branch on the same list, as CI printed it on the runner: 1801 passed, 3 failed (the sidebar foot's three fullscreen checks, on the runner only), 10 known, 18 unstable; locally in-process 1801 passed, 2 failed, both the boot race and both green on rerun.

The 19 specs that reach inside the main process (`spyPtySpawn` on `pty:spawn`, the dialog and clipboard stubs, the menus) stay as they are: their subjects have not moved to the server in this wave, and a client that does not exist yet cannot assert them. They move with the sessions in wave 2. Wave 2, lane B (PRDCT-3240): the five that spied on terminals (`spyPtySpawn` on `pty:spawn`, the tap on `pty:write`) read the terminal journal the app writes under `--test-no-activate` instead and pin `server: 'in-process'`, since an attached server has no terminals until wave 3; the taps on the session writes are the sessions lane's; the dialog, clipboard and menu stubs stay the shell's, and so do the two specs that stub `pty:spawn` rather than spy on it (`claude-chat-adapter`, `provider-usage`).

### CI

`.github/workflows/checks.yml` gains an end-to-end job on `macos-latest` for pull requests and pushes to `dev` (Bun and tmux installed by the job, the app built from the checkout). What it proves: the server spec passes with the server in-process and with the server attached to its own process. Those two steps are the gate and fail the job. What it does not prove: the rest of the suite. The whole suite runs in-process as a third step with `continue-on-error`, its result line written to the job summary, because on 2 October 2026 the suite on `dev` is not deterministic across machines (the figures above) and a gate that is red on a healthy branch is a gate nobody reads. That step becomes a gate by dropping `continue-on-error` once the unstable specs are fixed (PRDCT-1762 and PRDCT-2542 name the boot race and the launch timeout; PRDCT-1711 carries the thread). Its first run, on the draft pull request that proved the job, took 32 minutes. The release rail (`release.yml`, `build-win.yml`) is untouched.

## Consequences

- The app works at every merge, and the server is a swap of one line when the package lands; nothing on screen changes in this wave.
- The server's packaging as a second binary is not in `electron-builder.yml`. Listed debt, with the out-of-process server's release.
- The PTY sidecar, the durable event store adapter and the move of the sidebar truth are wave 2's, batched again from what wave 1 merged. Out of both waves: the plugin host, git, GitHub, SSH, locations, OpenClaw, linked documents, a browser client.
- The e2e suite on `dev` carries failures that predate the split and do not depend on it. They are named in `known-failures.json`, printed in every run, and the unstable specs are off the gate by name rather than by a filter that would hide a crash. Fixing them is the work PRDCT-1762 and PRDCT-2542 describe, not this lane's.

## Wave 2: the sessions on the server (2026-10-06, PRDCT-3239)

The framework is pinned at 0.3.0 (every `@structure-ai/*` exact, `@structure-ai/grpc` beside them for wave 3's terminal process, one copy of Effect), which supersedes the 0.2.1 pin above.

**The per-domain pattern** every later lane follows: in `packages/contract`, one module per domain (its commands, queries and failures), the shared failures in `errors.ts` (`CapabilityUnavailable`: what the server reached cannot do, by what it is, answered 422 with a sentence the window shows), its events as members of `ServerEvent`, its group as one line in `api.ts`; in `packages/server`, one folder per domain with `port.ts` (a `Context.Tag` with `layer(service)` and a `none`) and `handlers.ts` (where a thrown error becomes a declared failure), the ports an entry provides gathered in `ports.ts` (`ServerPorts`) and composed in `runtime.ts`; in `packages/client`, one module per domain built from the one `call` (`call.ts`); in the preload, one section per domain, every method a `viaServer` route with its IPC arm. The shell's implementation of a port is one entry in the `ports` main's boot passes to `startClaveServer` (required, never defaulted).

**Sessions** are the first domain through it. A window's list, get, start, stop, write (the shell prepares a user message's attachments at the write), view, models, commands, capabilities and history go over HTTP; the stream and the exit over the push channel, whose client answers a subscription with the server's own `subscribed` frame once the session is ready and its listeners bound; a session's title, plan, clear and state are server events to every attached client, and the per-window sends are kept only for an app without a server (`src/main/server/session-events.ts`: one or the other, never both). The shell answers every call from one session host (`src/main/sessions/host.ts`), the IPC handlers and the server's handlers alike; starting and stopping moved out of the PTY handlers into `sessions/lifecycle.ts`. The server does not check which window owns a session: every window of one app holds the same token, the one trust domain the loopback server knows; the IPC handlers keep the check for a window the server has not reached.

**Attached, the endpoint is published** to the windows, which wave 1 withheld. A standalone server has no terminal process until wave 3, so it runs on `SessionHost.none`: the list and a start answer `CapabilityUnavailable` naming the missing part, and the window shows that sentence where the sessions would be (`ServerNotice`, over the stage), never an empty list or a chat that never mounts. The preload relays the refusal to the page (an Error crossing the context bridge keeps its message and loses its tag); `tests/e2e/server-sessions-attached.spec.mjs` pins it in the built app. `npm run dev:attached` is therefore a server-development mode in wave 2, not a way to run sessions.

**One transport, and one signal for the late window.** The shell publishes a session's title, plan, clear and state on the server when it runs and sends them to the window over IPC only when it does not (`session-events.ts`, and the same gate on a terminal's hook state in the PTY handlers), never both. A window that boots before the server is named binds its listeners on IPC and joins the push channel through the preload's one `onServerAvailable` signal, fired when any routed call connects or when the preload's watch finds the server (asked of main every two seconds); every domain's push listener joins that signal, with its catch-up read inside its own wiring. A session's subscription is released on the transport it was taken on, and a stream listener stays on IPC while the subscription is IPC's.

**The end-to-end seam.** Under `--test-no-activate` main exposes the session host at `globalThis.__claveE2E.sessionHost` (a namespace shared with the other domains, created when absent and extended in place); the specs that wrapped `ipcMain._invokeHandlers` to see what the composer wrote wrap the host's methods instead, and the harness's spawn spy taps the host's `start` beside `pty:spawn`. A spec that needs a fixture inside the process runs the app with its in-process server; the shared attached-mode fixture seam is wave 3's, beside the terminal process.

## Wave 2: the settings on the server (2026-10-06, PRDCT-3242)

**Settings** are the second domain through the server: the Claude and Codex account lists, the login jobs, the usage reads of both providers and Pi, the launch profiles, the app icon, and the workspace registry and pins, behind one settings port (`packages/server/src/settings/port.ts`) and the same handlers whatever the entry. Inside the app the port is the shell's own managers (`src/main/settings/shell-source.ts`), passed by main beside the session host; the settings IPC handlers call that same source, so the IPC route and the server route read one truth and one stream of events. Every settings command declares `SettingsRefused`, a manager's refusal with its sentence (a token that is not one, a reserved profile id), which the window shows as it did over IPC; the two terminal logins, a login's input and cancel, and the app icon also declare `CapabilityUnavailable`. A token or an API key travels in one command only, redacted in the contract and opened in the handler; no answer, list, event, push frame, log line or file carries one in clear. A settings change reaches a window over the transport it is on: main fans it out over IPC and over the server's events, and the preload listens on exactly one, IPC until the push socket is welcomed and while it is down, the push channel while it is open (`src/preload/dual-listener.ts`); the two workspace writes carry the writer's window key, which the change event carries back so the writer drops its own echo.

**Attached, the settings diverge from main's.** The standalone entry serves the same managers from its own `--data-dir` on the standalone ports (the macOS Keychain for the secrets) and refuses the three commands it cannot carry. Since lane A publishes the attached endpoint, an attached window reads and writes the standalone's settings, while what main reads for itself (among them the first window's workspace, a window's switch of workspace, the Window menu's workspace list, the PTY's account tokens, the MCP server's reads, the five-minute usage poller) stays on main's managers under the app's own user-data directory: a workspace registered from an attached window is not one main can switch to, and an account added there is not one a session can start on. `npm run dev:attached` is a server-development mode in wave 2, for the settings as for the sessions; one truth comes with wave 3, when main's own readers move to the server with the terminal process. The eight end-to-end specs whose quota fixtures stub the shell's source (`globalThis.__claveE2E.settings`, under `--test-no-activate`) pin the in-process server for that reason; `tests/e2e/settings-attached.spec.mjs` proves the standalone serves the settings and that an attached window's writes land there.

## Wave 2: the Antasphere account on the server (2026-10-07, PRDCT-3259)

The optional login of Clave itself with an Antasphere account is a settings domain of the server, owned by the settings source whichever entry runs it: the manager (`src/main/antasphere-account.ts`) runs the flow, the token exchange and validation, the sealed session, its renewal and its sign-out, in the app's process while the server runs there and in the standalone server's when it runs alone, where the session is sealed in the macOS Keychain, serialised to printable ASCII first. Attached, the shell builds no manager: nothing under the app's user data is restored or offered as a login, and the IPC route refuses. The status is the one read model every client gets (`GET /accounts/antasphere`, the `accounts.antasphere_changed` event); the four commands move it.

The browser is the shell's. A sign-in answers the _handoff_ (the authorization URL bound to the login's generation) in the command's direct answer to the client that asked, and in nothing else; the preload confirms it with the manager that issued it (`POST /accounts/antasphere/handoff/confirm`, the URL redacted, a read that starts nothing) and hands it to main, which checks the target against its own issuer and opens it. A standalone server opens no browser. The confirmation and the OS open are two steps, not one transaction: the manager's exact-handoff check, the preload's own operation order (bumped synchronously by a cancel, a sign-out, a newer sign-in and a status saying the login is over) and the store's ordering close everything the client hears before it hands the URL to the system; a cancel on the server after that lands on the manager's callback check. `docs/antasphere-account.md` carries the detail.

## Wave 3: the terminal process (2026-10-08, PRDCT-3292)

**The terminals of a server running on its own come from a Node process beside it.** node-pty works under Node and not under Bun (the measurement in Context), so the standalone Bun server keeps no terminal of its own: `src/main/terminal-process/` is the process that owns node-pty, started from the bundle electron-vite writes beside the main process (`out/main/terminal-process.js`, the `terminal-process` input of `electron.vite.config.ts`; it cannot run from its sources under plain Node, since the framework ships sources too and Node strips no types under `node_modules`). It serves the Terminals port of `packages/server/src/terminals/port.ts` as gRPC on the loopback with `@structure-ai/grpc` 0.3.0, insecure transport and the token every call must present, checked in `verify` before any handler and in constant time. The server's side is `grpcTerminals` (`packages/server/src/terminals/grpc.ts`), the port over the framework's client, which `server-entry.ts` gives `ports.terminals` under `--terminals <host:port>` with the token in `CLAVE_TERMINALS_TOKEN` (read once and taken out of the environment, the rule of the server's own two variables: the deletion keeps it from the children both processes spawn, while `ps -eww` on macOS still shows the environment a process was started with); without the flag the entry says so on stderr and runs on `Terminals.none`. The sessions of the standalone server stay on `SessionHost.none` in this lane: composing the session host over these terminals is lane C's (PRDCT-3293).

**The wire contract** (`packages/server/src/terminals/proto/terminals.proto`, package `clave.terminals.v1`) keeps a terminal's life apart from any one call. Spawn, Write, Resize, Kill and Ping are unary; Attach is one server stream per terminal carrying the output and the exit as sequenced events. The framework caps every call, an established stream included, at `maxCallMs` (30 s by default, 24 hours at most), and a terminal may live longer than a day: the process serves with the 24-hour ceiling, the server's side opens each attach stream with a one-hour deadline and, when it ends on DEADLINE_EXCEEDED, re-attaches with the last sequence it saw; the process keeps the recent output of every terminal (512 KiB) and replays what the caller missed, with a `Gap` event naming what it no longer holds. Writes, resizes and kills go one at a time per terminal, each sent once the one before answered, so keystrokes keep their order without a second long stream to resume; consecutive writes waiting together go as one message. The port's `spawn` stays synchronous (the terminal backend starts a process in the middle of a resize and cannot await): the handle is returned at once, what is written before the process answers waits in its queue, and the pid is 0 until known. The two declared failures, `SpawnRefused` with node-pty's reason and `UnknownTerminal`, cross the wire as the framework's business failures (protobuf bytes in a trailer, nothing else of an error does). The generated Protobuf-ES code is **checked in** beside the proto and regenerated by `npm run proto:gen` (buf and protoc-gen-es from the dev dependencies, no protoc); the checks workflow regenerates and fails on a diff, so a proto edited without its generated file is caught before it fails at runtime.

**A process that is gone is said, not guessed.** The server's side marks the process down on the first UNAVAILABLE, or on a refused token (a wrong token never becomes right), and keeps it so (the process starter never restarts it); a ping that merely times out, a process alive and late, answers not ready for that read and nothing more, because a stall must not end every terminal (round 1 of the lane's verifier stalled the process 3 s with SIGSTOP and watched the first design do exactly that). Down, every open handle ends with an exit of code 1 and the sentence in the log, a new spawn throws `CapabilityUnavailable` naming the process and its address, and `TerminalsService.ready` (optional on the port: a port in this process has nothing to ask) is registered as the `terminals` check of the framework's readiness in `runtime.ts`, so `GET /health/ready` answers `ready: false` with `checks: [{ name: "terminals", ok: false }]`. The other way round, a terminal nobody has attached to for 15 s is hung up by the process (SIGHUP, then SIGKILL after another 15 s), because the only reason is a server that died; and the process itself stops when the parent it was given (`--parent <pid>`, polled every two seconds) is gone, so a server that died without a word leaves no terminal process behind.

**The process starter** (`scripts/server-process.mjs`) starts the terminal process first, reads its one announcement line (`{"address","token"}`, the server's own shape), then the server with the address on its command line and the token in its environment, and stops them in that order; `terminals: 'none'` starts the server alone for a caller with no bundle (the server's own unit tests on the Linux job), never as a fallback: a missing bundle is an error naming the build to run. `npm run dev:attached` therefore builds before it starts. The harness's attached mode gets the terminal process with every server it starts.

**Bun 1.4.1.** The framework's gRPC package needs it (its README: Bun 1.3.14 fails the retained backpressure reproduction). Rather than changing the Mac's own Bun, the `bun` npm package is a dev dependency pinned at 1.4.1, `bunBinary` prefers `node_modules/.bin/bun` to the PATH (after `CLAVE_BUN`, the explicit override), and `checks.yml` pins the same version for anything else that calls `bun`. The proof that the server's side works under that Bun is `src/main/terminal-process/probe.ts`, run by `scripts/server-process.test.mjs` with the repository's Bun against a terminal process started from the bundle; the Linux unit-test job skips the bundle-gated cases and the macOS e2e job runs them after its build.

**Listed debt.** The terminal process is not packaged with the app (no second binary in `electron-builder.yml`, with the out-of-process server's release). A process down stays down until the pair is started again; a restart of the terminal process under a running server is not built. The output kept for a re-attach is bounded by bytes, so a terminal that writes more than 512 KiB during the millisecond of a re-attach loses it, said by the `Gap` event.

## Wave 3: the sessions on the separate server, and the suite's one way in (2026-10-08, PRDCT-3293)

**The session host loads without Electron.** Nine import chains tied `src/main/sessions/host.ts` to the desktop app after wave 2; each is behind a port now. The window the host still needs is a KEY and a session windows port (`src/main/sessions/windows.ts`: the workspace a window shows, the binding of a session to its window, the per-window arm of terminal bytes and exit and of a session's news when no server publishes them, and what a window owes before its session stops, the linked-document flush); the shell implements it over its window registry and `webContents.send` (`sessions/electron-windows.ts`, installed by the PTY handlers at boot), the standalone server keeps the bindings in a map and sends nothing, since a window on the server reads everything off the push channel. The title generator and the session events take a window key, never a window object. The copy offer keeps its store and takes the clipboard and the broadcast from the shell through one installed port; a process without one keeps the offer and refuses the copy with the reason. The Claude adapter writes a session's `--mcp-config` through the terminal layer's MCP config port rather than importing the MCP runtime, which is the shell's. The lifecycle reads the tmux switch through a reader the shell installs at boot (the `.clave` handlers' own preferences file, `clave-preferences.json`, where the app keeps it); a host that installs none, the standalone server, runs tmux, the default. `src/main/sessions/host-graph.test.ts` fails the import if a chain comes back.

**The standalone server runs the app's own session host** (`src/main/sessions/standalone-host.ts`, wired by `server-entry.ts`): the same host over the same manager and lifecycle, its terminal layer's documents under the server's `--data-dir`, a session's process from the terminals port the entry provides (lane B's terminal process over gRPC; `Terminals.none` names what is missing when it is not wired, and a resize on a terminal then answers `CapabilityUnavailable`), and no MCP server behind the MCP config port, so a Claude session starts without `--mcp-config` until the agent tools reach the server (lane D). A chat session runs its CLI as a child of the server process. The session events (title, plan, clear, state) go out on the server's own push channel from the standalone entry as from the in-process one (`publishSessionStates` and the publisher in `server/session-events.ts`).

**The terminal pane on the attached server.** The sessions contract gains `ResizeSession` (`POST /sessions/resize`): the first size starts the process at the pane's real size, as the shell's `pty:start` did, a later one resizes it; the host's bytes take the lifecycle's `writeTerminal`, so the `/clear` watch and the test journal see them as they see the IPC bytes. The endpoint main names to the preload carries its `mode`, and the preload routes the pane's start, resize and bytes to the server ONLY when the app is attached (chained per session so the bytes keep their order over HTTP), hearing the `pty` frames and the exit off the push channel there and over IPC inside the app, never both: inside the app the bytes stay on IPC, where they are ordered and cost nothing, and a push subscription beside the IPC listener would deliver every byte twice. A write frame on the push channel is the next step for the attached pane's latency, not this wave's.

**One way into the sessions for the suite, in both modes.** The server has a test fixture route, `POST /e2e/evaluate` (`packages/server/src/fixtures/route.ts`): it runs a function source in the process hosting the sessions, with `globalThis.__claveE2E` as the specs know it, and answers the function's awaited value. It runs code it is sent, so it is TEST-ONLY by construction: registered only when the entry is started with `testFixtures`, which the app and the standalone entry set from `--test-no-activate` (the harness passes the flag to both; the packaged app never does), so a server started without it has no such path and answers 404; it sits inside the token check (401 without the token) on the loopback bind. `route.test.ts` pins the three gates. `launchApp` hands every spec one `fixture` handle for whichever server runs (`serverFixture`, `appServerFixture` in `harness.mjs`), passes the app's test flags to the standalone server (`--test-no-activate` turns its fixture route, its terminal journal and its hooks namespace on; `--dev-echo-adapter` reaches the process that spawns the sessions), and copies the settings documents a spec seeded into the app's folder into the server's before it starts (`SEEDED_DOCUMENTS`, `registerSeededDocuments` for the other lanes' files; the app and the server never share a folder, since both write `clave-server.json` and the same settings files). The chat specs launch through `launchApp` and wrap the host through the fixture; a synthetic frame is injected where the session lives (`__claveE2E.echo.inject`) and reaches the window over its own transport. What still needs Electron (an `ipcMain` stub, a window's size, the clipboard) stays on `app.evaluate`, and a spec that opens its session through the agent tools stays pinned in-process until lane D answers the tools from the server.

**What the attached mode still lacks, named.** Two things measured on 8 October 2026 and left for the next lane rather than hidden behind a pin without a reason. The restore of persisted sessions: on an attached server the session records are the server's, but the window's restore at boot still reads main's own list (`pty:list`) and main's folder, so a session that survived a quit is not brought back on the next launch of an attached app; the restart specs (`terminal-reattach`, `chat-tab-restore`, `chat-history-pages`, `agent-launch-profiles`, `multi-window-migration`, `codex-chat-tab-restore`) pin in-process and say so. The plugin host: a chat's views are plugin views leased from the shell's plugin host, which knows main's sessions and not the server's, and a plugin's own adapter and launch profile register with main's managers while an attached window reads its profiles from the server; a chat on the standalone server mounts but gets no view lease, so the chat specs and `plugin-provider` run in-process, through the same fixture, until the plugin host reaches the server. In-process the terminal pane's road stays the synchronous IPC send it always was: a write that first waited on a promise reordered against the pane's own start, and the mode is known before any pane exists, so only an app known to be attached takes the server road.

## Wave 3: the workspace files on the server (2026-10-08, PRDCT-3291)

**The `.clave` files** are the next domain through the per-domain pattern: read, written, watched and trusted by the server, behind one port (`packages/server/src/workspace-files/`, the class `WorkspaceFiles` in its light entry `@clave/server/workspace-files`, which imports no Effect so the shell builds it at boot). The parser, the writer, the trust store (the trusted roots and the trusted content hashes, two JSON documents behind the entry's storage) and the per-file directory watchers moved there from `src/main/ipc-handlers/clave-file-handlers.ts`, which is now the IPC arm over the shell's one instance (`src/main/workspace-files.ts`); the trust boundary (`describeElevated`, `sanitizeElevated`) moved with its tests to `trust.ts` beside the class, and the app's CLAUDE.md names the new places of the six-place mirror rule. In the app the in-process server is handed the shell's instance, so a window on IPC and a window on the server read one truth and one trust; the standalone entry builds its own over `--data-dir`, so an attached window's trust is the standalone's, as its settings are.

**The review is a round trip.** The server may have no window, so it never shows a dialog: a read that meets an elevated file nobody trusted publishes `workspace_files.review_needed` (the file, the folder the checkbox would trust, the commands, the prompts, the permissions flag, and the `requestId` the reader sent) and HOLDS the read until `AnswerWorkspaceFileReview` names that review, or until five minutes pass, which reads as Cancel: silence is not trust. The dialog stays Electron's, in the shell. A window whose read went over IPC gets it from the IPC handler directly; a window whose read went through the server hears the event on the push channel, recognises its own `requestId` (`src/preload/workspace-files-relay.ts`), asks main over IPC to show the same dialog (`clave:review-dialog`, one text builder for both roads) and answers the server itself. Two guards come from wave 2's findings: the preload waits for the push welcome before it sends a read through the server, so the event cannot be published before anyone listens, and a watch taken over IPC before the server was named is re-taken on the server once it is and released on the transport that holds it, so a change never lands where the window stopped hearing. A watched file's change is `workspace_files.changed` to every client and `clave:file-changed` over IPC to every window; the preload's dual listener hears exactly one.

**The harness.** `stubReviewDialog` keeps proving both roads, since the dialog it replaces is the one both call. In attached mode the server's trust store is its own data directory, so a trusted root the spec seeds in the app's folder reaches the server through the harness's seeded-documents copy (lane C's, `clave-trusted-roots.json` among them); `tests/e2e/workspace-files-attached.spec.mjs` proves the read, the review round trip, the watch and the separation of main's store from the server's.

## Wave 3: the agent tools are served, first part (2026-10-08, PRDCT-3294)

The MCP layer stays `@modelcontextprotocol/sdk` in main, with its own listener on the loopback, the per-tab token and the instructions block exactly as before: Valentin decided it on 8 October, after a survey of `@structure-ai/mcp` 0.3.0 found no server-level instructions in it, and Clave's instructions block is what makes agents call its tools (`CLAUDE.md`, the gotcha on the truncated block). What moved is everything behind the SDK's tool handlers.

**The view request.** Until this wave twenty of the twenty-three tools asked a window over Electron IPC (`mcp:command` to the window's web contents, `mcp:response` back), because the sidebar truth was each window's. The windows now reach the server, so the bridge is a domain of the server (`packages/contract/src/views.ts`): main's MCP server sends `RequestView` with the key of the window the command is for (the routing stays main's, `mcp-server.ts`: the subject tab's window, the named window, the caller's, the focused or primary); the server pushes one `request` frame to every welcomed peer (it does not know which socket is which window, and a request is a question rather than a fact, so it never enters the event store); the window whose key it is runs the command in its dispatcher as before and answers with `AnswerViewRequest`; the server resolves the waiting request with the window's result, or its refusal (`ViewRequestRefused`, the window's own message) or the deadline (`ViewRequestTimeout`, ten seconds unless the caller says otherwise, a minute at most). The preload listens to the frames on the push client and answers through the client; the IPC pair stays in the preload for the end-to-end harness's `callMcp`, which drives a window's dispatcher directly, and main never sends it. Main reaches the server through the same typed client the windows use (`src/main/mcp/server-client.ts`, loaded on the first tool call, never at boot), on the address it published itself.

**The served tools.** A tool whose work is a command or a query the server already has calls it through the client instead of asking a window (`src/main/mcp/served-tools.ts`): `clave_list` (the sessions and the layouts of every window, with the pinned groups and the focused tab asked of the caller's window, since the workspace files are lane A's and not yet on the server), `clave_create_group`, `clave_rename` of a group, `clave_set_group_view`, `clave_move_session` into a group and to another window, `clave_add_group_terminal` (the terminal added to the layout, its session started through the server with the group-terminal link, then linked), `clave_close_session` (the session stopped, the serving session of its view stopped, the session removed from its window's layout, the close recorded with its closer). The windows hear every change over the push channel, so what a served tool does is on screen the moment the server tells the window. Two rules joined the renderer for it: a tab the server's layout no longer places and whose process has ended leaves the window's store instead of being appended and saved back (a side panel with unsaved edits keeps its tab), and a terminal whose session the window never saw is taken in from its record. The tools kept on the window, through the view request: a rename of a session, a switch of account, a read of a tab's screen, a message typed into a tab, the opening of a session (the account pool is the renderer's), the launch of a pinned group, the view attached to one tab (the server's `SetSessionView` is the chat view id, not the page on a tab's row), and the actions that are a window's by nature (focus, open a file, notify, the side panel, open a window, switch workspace). A move into a group of another workspace also keeps the window, which is where a tab's workspace is aligned to its group's. The commands those need are wave 4's.

**Attached**, to a server that hosts no windows, the sidebar's road is the shell's (wave 2, lane C), so the served tools fall to the window through the view request, which the attached server carries: they never write the standalone's layouts. Under `--test-no-activate` main records which road each tool took on the shared hooks namespace (`globalThis.__claveE2E.mcpRoads`), which is how `tests/e2e/mcp-served-tools.spec.mjs` proves a tool was served and not merely answered.

## Wave 4: a window hears the server whenever it opens (2026-10-10, PRDCT-3295)

**Every server-event listener of the preload waits for the server instead of asking once.** The listeners the window binds at start on both transports (`viaServerEvent` in `src/preload/index.ts`: the workspace registry and pins, the Claude and Codex account lists, the login progress, the two usage reads, the Antasphere status, and the `.clave` file changes) handed `dualListener` a backing asked of the method router once, at bind time; a window that bound them before main named the server was told null and stayed on IPC for the rest of its life. In the shipped app the one shared instance's IPC fan-out hid it; attached, main's IPC fan-out is main's own managers, so that window never heard a change the server made (wave 3's lane A met it on the file watch, round 5 of its verifier on the real app, and fixed that one listener by waiting on `onServerAvailable`, dropping the withdraw). `dualListener` now takes a WAIT (`onPush`: run `ready` once a push client exists, at once when it already does, and answer the function that withdraws it), which `viaServerEvent` fills with the preload's own `onServerAvailable`, the signal the sessions' listeners already wait on; the unsubscribe withdraws a wait that has not fired, so a listener bound and released before the server comes leaves no waiter behind, the leak wave 3 recorded. The file-change listener is `viaServerEvent` like the others.

**The catch-up is the listener's.** A window whose state came from main over IPC must land on the server's: each family names its read model (`catchUp`, the account list, the usage snapshot with its cached errors left out as the renderer's own prime leaves them, the login list, the Antasphere status, the workspace state) and `dualListener` reads it at every welcome the listener witnesses, in the welcome's own tick after the IPC listener is dropped, delivering each value to the callback as if it were an event. While the read is out, the push events of the tag are held and delivered after its answer, in their order, so the window ends on the newest state whatever the two roads' timing and a usage read of one account never costs the others their catch-up; an event the pick drops, the window's own echo, marks the answer stale (the window wrote after the read went out) and the answer is dropped while the held events are delivered; a second welcome while a read is out supersedes it (round 1 of the lane's verifier reproduced the three orderings against the real preload); a socket drop while a read is out hands the window back to IPC, so what was held is delivered at once and the read is abandoned, the next welcome reading again (round 2 found the held events landing after a newer IPC value). The hold lasts as long as the read, at most the request client's ten-second timeout, after which the failure path delivers what was held. A refused read (a standalone server runs no login job and may hold no Antasphere account) delivers nothing and what was held is delivered. A listener bound on a socket already open reads nothing: the renderer's stores read the server themselves, though three of them (`loadClaudeProfiles`, `loadCodexAccounts`, `bootWorkspaces`) read before they subscribe, a gap older than this lane and left as it is. The sidebar's wire keeps its own catch-up (the layout read on `whenOpen`, dropped by revision), which this generalises without replacing. `src/preload/dual-listener.test.ts` pins the wait, the withdraw and the catch-up; `src/main/sessions/preload-server-events.test.ts` binds every family before the server is named and proves it hears IPC, then the server's state, then the push channel, and leaves nothing bound when released early; `tests/e2e/server-events-early.spec.mjs` attaches the app to a server main names eight seconds late and changes the server's registry, accounts and usage through its API, each heard once by the listeners bound before it (the drop of the IPC listener itself is the unit tests' to prove: attached, main's IPC carries nothing of the server's change).

## Wave 4: a quit and an end-to-end check that cannot stall (2026-10-10, PRDCT-3375, PRDCT-3290, PRDCT-1762)

**Where the ten seconds went.** Every quit of the app with its in-process server took ten seconds, on dev as on the lanes (93 quits measured across waves 3 and 4), and wave 3's verifier saw one quit of 787 s under load and two CI runs stalled to the job's ceiling. Measured before anything was changed: the server's stop alone, with a real push client attached, a warmed keep-alive connection or a request fired into it, takes 2 to 9 ms; in the app the listener refused new connections 0.7 s into the quit and the process lived to 10.0 to 10.3 s, two connections from the window to the server's port open until about 9 s. The previous order (the hub closed, the scope closed, Node's `server.close()` last) left the listener accepting while the peers were told, and then waited on every connection the window still held, until the client's own 10 s request deadline let go. A request accepted in that window was never answered (wave 3, lane A, round 3, m6).

**The stop, in a fixed order** (`packages/server/src/embedded.ts`, `stopEmbedded`): the listener is this entry's own, so the stop closes it first (a connection a client opens from here is refused at once, and the platform layer's own close, later, finds nothing listening); the requests already inside a handler are answered while the handlers stay attached, bounded by `STOP_DRAIN_MS` (1 s); the push peers are told with `CLOSE_SERVER_STOPPING` and given `STOP_PEER_GRACE_MS` (250 ms) to answer the close frame, a peer that does not is ended, because the ws server's close inside the scope would otherwise wait on it for its own thirty seconds; the scope closes (handlers off, hub disposed, ws server closed); whatever a client still holds is destroyed, so the listener's close completes and a request landing on such a socket afterwards is refused by the reset, never left hanging. The stop answers a report (how long, requests in flight and whether all were answered, peers told, connections destroyed) that main writes to its log as one line.

**The quit is bounded and names its wait** (`src/main/quit-cleanup.ts`, used by `before-quit` in `src/main/index.ts`): the two waits of the cleanup, the sessions' shutdown and the server's stop, are awaited under a ceiling of `QUIT_CEILING_MS` (8 s); past it the log says which of them is still pending and the quit goes on; a quit that still has not ended `QUIT_HAMMER_MS` (2 s) later is exited with code 1. A ceiling alone would have hidden the stall PRDCT-3290 saw once for twenty-six minutes; the line in the log is what lets a next occurrence name itself. The title generator holds the handle of its one-shot `claude -p` and `cancelAll` ends it with the sessions' shutdown (`pty-manager.ts` `killAll`), in the app's quit and in the standalone server's stop alike, which both already call it; wave 3's verifier had found one alive after the server had stopped.

**The end-to-end run is bounded too** (`tests/e2e/bounds.mjs`): the runner gives every spec a deadline (`SPEC_DEADLINE_MS`, ten minutes; a spec exports `deadlineMs` for its own, `CLAVE_E2E_SPEC_DEADLINE_MS` overrides for a run), past which the spec fails on one named check, every app the harness launched is killed by its exact pid and every server it started is stopped, the dead spec's later checks are printed as LATE and counted nowhere, and the run goes on; `app.close()` is bounded at `CLOSE_TIMEOUT_MS` (25 s, above the app's ceiling and hammer so the app speaks first) and ends with the Electron pid killed; every synchronous child call of the harness (`lsof`, `tmux`) has a timeout, because a hung one blocks the runner's own event loop, the one shape no in-process deadline can catch (wave 3's launch whose runner did not turn for thirteen minutes). And the launch waits on the boot, not on a clock (PRDCT-1762): the renderer marks its document `data-boot="complete"` once its boot tail has run (the saved layout merged, the survivors adopted, persistence on) or `data-boot="restore-prompt"` while it waits on the person, and `launchApp` and `openWindow` wait for that mark, `launchApp` for the server's discovery file too, with a 60 s timeout that names what was missing; a `settleMs` a spec passes is waited after the mark, and the default is zero. Four specs listed unstable for the boot race leave `known-failures.json` as they pass.
